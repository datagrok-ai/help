The deployment consists of a few docker containers, a [database](../../develop/under-the-hood/infrastructure.md#1-core-components)
for storing metadata, and [persistent file storage](../../develop/under-the-hood/infrastructure.md#1-core-components)
for storing files.

This document contains instructions to deploy Datagrok using [CloudFormation](https://aws.amazon.com/cloudformation/)
on [AWS EKS](https://aws.amazon.com/eks/) with [AWS RDS](https://aws.amazon.com/rds/) (PostgreSQL) and
[AWS S3](https://aws.amazon.com/s3/). The template provisions the EKS cluster (or uses yours), RDS instance, S3 bucket,
Application Load Balancer, IAM roles with [IRSA](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html),
and installs the Datagrok [Helm chart](../k8s/install-helm-chart.md) on the cluster automatically.

We considered a lot of typical security nuances during the CloudFormation template development. As a result, you will
create a Datagrok infrastructure in AWS that applies to all standard security policies.

More information about Datagrok design and components:

* [Architecture](../../develop/under-the-hood/architecture.md)
* [Infrastructure](../../develop/under-the-hood/infrastructure.md)
* [Helm chart install](../k8s/install-helm-chart.md)

:::tip Migrating from ECS?

The EKS templates share the database, bucket, secrets, and load balancer with the [ECS templates](deploy-amazon-ecs.mdx).
Replacing an ECS stack's template with the matching EKS template keeps your data and your URL. See
[Migrate from ECS](#migrate-from-ecs).

:::

## Prerequisites

1. Check that you have the [required permissions](https://github.com/datagrok-ai/help/blob/master/deploy/iam.list)
   on the AWS account to perform CloudFormation deployment to EKS.
2. The private subnets need outbound internet access (NAT gateway). The cluster pulls Datagrok images from Docker Hub,
   and the installer downloads Helm and the chart.

## New or existing cluster

By default, the stack creates an EKS cluster with a managed node group (`NodeInstanceType`, `NodeGroupDesiredSize`)
in the private subnets. Set `GpuRequired` to `true` to add a GPU node group for GPU plugins.

To install Datagrok on a cluster you already run, set `ExistingEksClusterName` to its name and use one of the
`vpc-eks-*` templates with the cluster's VPC. The stack then skips the cluster and node groups, and:

* adds the cluster's IAM OIDC provider if it has none;
* opens RDS and the load balancer to the cluster security group;
* installs the [AWS Load Balancer Controller](https://kubernetes-sigs.github.io/aws-load-balancer-controller/)
  only when the cluster does not run one;
* installs Datagrok into the `HelmNamespace` namespace (`datagrok` by default).

The existing cluster must meet these requirements:

* Its authentication mode is `API` or `API_AND_CONFIG_MAP`. The stack grants its installer access with an EKS access entry.
* Its nodes use the cluster security group (the default for managed node groups) and have enough free capacity
  for Datagrok (about 4 vCPU and 8 GiB).
* Its API endpoint is reachable from the private subnets.

The stack installs Datagrok with a CodeBuild project. If an install or an update fails, open the build log from the
_DatagrokInstallerLogs_ stack output.

<TabItem value="r53" label="Yes" default>

##### Requirements

1. Create a [Route53 public hosted zone](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/CreatingHostedZone.html).

##### How to deploy

1. Use the [link](https://console.aws.amazon.com/cloudformation/home#/stacks/quickcreate?templateURL=https%3A%2F%2Fdatagrok-data.s3.us-east-2.amazonaws.com%2Fdeployment%2Fvpc-eks-r53-basic.yml&stackName=datagrok)
   to open the CloudFormation template and fill in all required parameters.

    1. [Specify stack name](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-using-console-create-stack-parameters.html).
       To meet AWS naming requirements, the name must be shorter than _10 symbols_ and correspond to
       [S3 Bucket naming rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html).
       We use 'datagrok' by default, but you may prefer to also specify the env in the stack name.

2. Wait until AWS completes the deployment. The stack status will be `CREATE_COMPLETE`.
   The script created a datagrok stand inside your existing VPC using the existing Route53 hosted zone.
   Your Datagrok instance is now ready to use.

   If you see one of the following statuses then something went wrong: `CREATE_FAILED`, `ROLLBACK_IN_PROGRESS`,
   `ROLLBACK_COMPLETE`, `ROLLBACK_FAILED`. [Check the stack events](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/troubleshooting.html#basic-ts-guide)
   for more information about the error.

3. Enter the platform at `datagrok.<subdomain>` using the `admin` user. To get the password:
    1. Go to stack Outputs. Find _DatagrokAdminPassword_ and click on the link to open AWS Secrets Manager.
    2. Click _Retrieve secret value_ and copy _password_. It is a generated password for the first admin login.
    3. To increase security, [change the password for the admin user](../complete-setup/configure-auth.md) on first login.
       Datagrok will ignore the admin password from secrets on subsequent restarts.

4. Complete the initial setup in the platform and you are ready to use Datagrok.

        2. Copy the AWS ARN for the imported certificate.

##### How to deploy

1. Use the [link](https://console.aws.amazon.com/cloudformation/home#/stacks/quickcreate?templateURL=https%3A%2F%2Fdatagrok-data.s3.us-east-2.amazonaws.com%2Fdeployment%2Fvpc-eks-dns-basic.yml&stackName=datagrok)
   to open the CloudFormation template and fill in all required parameters.

    1. [Specify stack name](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-using-console-create-stack-parameters.html).
    2. `DatagrokArnSSLCertificate`: specify AWS ACM ARN for `DATAGROK_DNS` from the prerequisites.

2. Wait until AWS completes the deployment. The stack status will be `CREATE_COMPLETE`.

3. As you chose the fulfillment option with external DNS, you need to create a CNAME record for Datagrok's Load Balancer.
   To get the Load Balancer endpoint for the DNS record:

        * Host: `DATAGROK_DNS`, Target: _DatagrokLoadBalancerDNSName_.

   in stack Outputs as described in the Route53 tab above.

## Service versions

Every service has a dedicated CloudFormation parameter (`DatagrokVersion`, `GrokPipeVersion`,
`GrokSpawnerVersion`, `GrokConnectVersion`, `JKGVersion`, `GrokRegistryProxyVersion`,
`RabbitmqVersion`) for picking the container image tag. Defaults track the most recent
Datagrok release and are tested together — see [Images and versions](../images.md) for the
current set and pinning conventions across deployment paths. `HelmChartVersion` defaults to
`DatagrokVersion`; the template appends `-helm` automatically (e.g. `1.27.3` → chart tag
`1.27.3-helm`).

## Update Datagrok components

You can update your Datagrok deployment without re-creating infrastructure. Before updating, we recommend backing
up the database and persistent storage. Refer to your internal backup procedures.

### How to update

Use the same [deployment script](#deploy-datagrok-components) and an updated version of the deployment profile:

1. Click **Update** > **Replace current template**, and provide the new template URL corresponding to your deployment configuration.
1. Specify new versions for image tags (see the [release history](../releases/release-history.md)). `HelmChartVersion` defaults
   to the same value as `DatagrokVersion`.
1. Click **Next**, skip optional settings, and proceed to **Review**.
1. If the stack enters a failed state (e.g., `UPDATE_ROLLBACK_IN_PROGRESS`), [check events](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/troubleshooting.html#basic-ts-guide) for details.

:::note

- CloudFormation will not replace the database or file storage during update.
- Your platform URL, admin credentials, and uploaded files will remain unchanged.
- Database schema migrations run automatically on the first start of the new app version.
- If you previously customized your deployment with environment variables, they will persist unless explicitly
  modified in parameters.

:::

## Migrate from ECS

If you run Datagrok on the [ECS CloudFormation template](deploy-amazon-ecs.mdx), you can move it to EKS by updating
the stack. The ECS and EKS templates define the database, the bucket, the generated secrets, and the load balancer
identically, so CloudFormation keeps them. Your users, files, settings, admin password, and URL stay the same, and
external DNS records keep pointing at the same load balancer.

1. Back up the RDS database and the S3 bucket.
2. In the existing stack, click **Update** > **Replace current template** and point at the EKS template with the same
   VPC and DNS options: `vpc-fargate-r53-basic.yml` becomes `vpc-eks-r53-basic.yml`, and so on.
3. Keep all parameter values, including the service versions. Change versions in a separate update.
4. Review the change set before you execute it. `DatagrokDB`, `DatagrokS3`, and `DatagrokLoadBalancer` must not appear
   in it with **Replacement** set to `True`. ECS services, task definitions, and the internal load balancer are removed,
   and the EKS cluster and the installer are added.
5. Execute the change set. The update takes about 30 minutes. ECS keeps serving until the Datagrok pods are ready.
   The pods then take over the load balancer target group, and CloudFormation removes the ECS services. Expect up to
   a minute of downtime during the switch.

If the change set replaces `DatagrokDB` or `DatagrokS3`, do not execute it. Contact
[support@datagrok.ai](mailto:support@datagrok.ai).
